HARD DAILY USAGE ENFORCEMENT - IMPLEMENTATION SUMMARY
====================================================

PROBLEM SOLVED
--------------
Users could still login and start sessions even after reaching their daily usage limit.
The blocking was soft - users could bypass it by creating new sessions.

SOLUTION IMPLEMENTED
--------------------
Hard enforcement that immediately denies ALL access when daily limit is reached.

KEY CHANGES
-----------

1. NEW MIDDLEWARE: validateUserAccess()
   Location: src/middleware/usageMiddleware.js
   
   Rules:
   - Check if request expired → 403
   - Check if user blocked (blocked_until > NOW) → 403
   - Check if limit reached (used_today_minutes >= daily_limit_minutes) → 403
   - Auto-block user if limit reached (set blocked_until = tomorrow)
   - Trigger Azure enforcement if enforce_in_azure = true
   
   Applied to:
   - POST /api/usage/start
   - POST /api/provision/request/:id
   - GET /api/provision/request/:id/credentials
   - GET /api/manage/request/:requestId
   - DELETE /api/manage/user/:userId
   - PATCH /api/manage/user/:userId/roles

2. PREVENT MULTIPLE ACTIVE SESSIONS
   Location: src/services/usageService.js
   Function: startUsageSession()
   
   Check:
   - Query: SELECT id FROM user_usage_sessions WHERE logout_at IS NULL
   - If exists: Return existing session, set alreadyActive: true
   - Prevents gaming the system by creating multiple sessions

3. HARD BLOCK IN STATUS ENDPOINT
   Location: src/services/usageService.js
   Function: getUsageStatus()
   
   Logic:
   - If usedMinutes >= dailyLimitMinutes → blocked: true, remainingMinutes: 0
   - Returns blocked state even if blocked_until not set yet

4. ENHANCED SCHEDULER
   Location: src/scheduler/usageScheduler.js
   Function: resetDailyUsageCounters()
   
   Runs: 0 0 * * * (midnight every day)
   Actions:
   - Reset used_today_minutes = 0
   - Clear blocked_until = NULL
   - Update last_reset_date = CURRENT_DATE
   - Log [USAGE_RESET] and [ACCESS_RESTORED]

5. AZURE ENFORCEMENT - REVOKE ONLY
   Location: src/services/usageEnforcementService.js
   Function: enforceUsageLimit()
   
   Actions when limit reached:
   - Revoke Azure RBAC role assignments (don't delete user)
   - Stop Azure resources (VMs, AKS, App Services)
   - Log action as 'limit_exceeded_revoke_access'
   - Preserve user account for next day access restoration

6. COMPREHENSIVE LOGGING
   New log messages:
   - [LOGIN_BLOCKED] - User denied access (with reason)
   - [LIMIT_REACHED] - User reached daily limit
   - [USAGE_RESET] - Daily counters reset
   - [ACCESS_RESTORED] - User access restored after reset
   - [SESSION_START_REQUEST] - Session start requested
   - [SESSION_START_SUCCESS] - Session started successfully
   - [SESSION_START_ERROR] - Session start failed
   - [ENFORCEMENT] - Azure enforcement triggered

HOW IT WORKS
------------

BEFORE (Soft Enforcement):
1. User reaches limit (used_today_minutes = 60/60)
2. User can still call POST /api/usage/start
3. New session created
4. Usage only updated when session ends
5. User could bypass limit by not ending sessions

AFTER (Hard Enforcement):
1. User reaches limit (used_today_minutes = 60/60)
2. User calls POST /api/usage/start
3. validateUserAccess middleware intercepts
4. Checks: used_today_minutes >= daily_limit_minutes → TRUE
5. Sets blocked_until = tomorrow midnight
6. Returns 403 Forbidden
7. User CANNOT start new session
8. User CANNOT access credentials
9. User CANNOT provision resources
10. At midnight: Scheduler resets counters, user can access again

  -H "Content-Type: application/json" \
  -d '{"requestId": 1, "userId": 1}'

SECURITY NOTES
--------------
1. Middleware runs BEFORE controller - request never reaches handler if blocked
2. Multiple session prevention - cannot game system by creating many sessions
3. Azure enforcement optional - set enforce_in_azure = true to revoke access
4. User accounts preserved - only access revoked, not deleted
5. Automatic restoration - scheduler resets at midnight, no manual intervention
